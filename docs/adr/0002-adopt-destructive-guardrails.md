# 0002 — 采纳(adopt)设破坏性防护:预览 + 确认 + 备份

## 状态

已接受

## 背景

**采纳**是指把 Agent 目录中游离的技能(孤儿)**收进仓库**、并把原目录
转为指向仓库的链接。它解决一个真实痛点:使用者已经装了技能,但技能
散落在各 Agent 目录里、不受仓库统一管理,随时可能丢失。

采纳的原始实现是**静默且不可逆**的:遍历每个 Agent 目录,把发现的
技能目录 `copytree` 进仓库,然后 `rmtree` 掉原目录、重建为链接。

这里有一个真实的危险:该操作**会物理删除 Agent 目录中的原始内容**。
如果遍历逻辑有误(例如把非技能目录误判为技能、或把不该采纳的目录纳入),
使用者会在**没有任何提示**的情况下丢失文件,且**没有回退手段**。
在单机、无备份的场景下,这是不可接受的数据丢失风险。

但它又确实需要保留:不采纳,孤儿就永远游离,仓库的"唯一真实副本"
承诺就不成立。

## 决策

保留采纳能力,但为其加**三重防护**:

1. **预览先行** — 执行前先扫描并**列出将被移动的每一项**(来源 Agent、
   技能名、原路径)。使用者看到确切清单后才决定是否继续。
2. **显式确认** — 预览与执行是两个独立步骤。不经确认,不执行任何
   文件移动。
3. **自动备份** — 执行前把将被删除的原目录复制到
   `~/.skills-hub/.backup/<时间戳>/`。备份成功前不得开始移动。

界面与 API 都遵循这个流程:`/api/adapt/preview` 只读、可反复调用;
`/api/adapt` 需携带明确的确认意图才执行。

## 后果

**正面**

- 破坏性操作变得**可预知、可回退**。
- 使用者能在预览阶段发现误判(如某个不该采纳的目录),及时中止。
- 备份目录本身成为一份安全网,即使采纳逻辑有缺陷也能恢复。

**负面**

- 流程从一步变三步,批量采纳时略显繁琐。这是为安全付出的代价,
  我们认为值得。
- 备份会**占用额外磁盘**(等于采纳内容的体积)。清理备份的时机
  交给使用者,程序不自动删除。

## 备选方案

- **保持静默不可逆** — 被否决:数据丢失风险不可接受。
- **只做预览、不做备份** — 被否决:预览能防"误判",防不了"执行中
  出错"。两者防的是不同的失败,缺一不可。
- **用移动(move)代替复制+删除** — 被否决:在同盘时更高效,但跨盘或
  跨文件系统会退化为复制+删除,行为不一致;且移动没有留下中间快照,
  更难回退。统一"复制到备份 → 复制进仓库 → 删除原目录 → 建链接"
  的步骤,失败点更可控。
